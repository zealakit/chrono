# Contributing to Zealakit Chrono

Thanks for helping. Chrono is a headless calendar and date/time library for Vanilla
TypeScript, React, Vue and Svelte. Read this page once; it is short on purpose.

## Setup

- Node (current LTS) and pnpm `12.18.0` (the `packageManager` field pins it).
- `pnpm install`, then `pnpm build` (core is built first; adapters resolve it from `dist`).

## Commands

```bash
pnpm check              # build + typecheck + test + lint + check:deps + check:independence + check:domains + check:size
pnpm readme:check       # README structure: EN/VI/CN parity
pnpm audit:api          # offline API audit: attribute vocabulary, messages, `any` in public types
pnpm examples:build     # the core example apps (a failure blocks a release)
pnpm release:check      # check + readme:check + audit:prod + check:standalone
```

Run `pnpm check` and `pnpm readme:check` before every pull request, and build the examples
(`pnpm examples:build`).

## Plans first

Every feature belongs to a numbered plan in `plans/` (`plans/00-conventions-as-built.md` lists
the conventions the code follows). Read the plan for the area you change, and update its
`Status:` line when you finish. A change that is not in a plan starts as a discussion.

## Hard rules

The rules live in one place: `.agents/AGENTS.md` (also reachable as `CLAUDE.md`). Read its
"Hard boundaries" section. The ones that surprise people:

- Chrono proposes changes and never persists, fetches or applies business rules.
- No CSS, no popup code, no dependency on another UI library in a Chrono package.
- Core is private and bundled into each adapter; never document it as an install target.
- Renaming or removing a `data-*` attribute or a `--chrono-*` custom property is a breaking
  change, because apps style against them.

## Tests and fixtures

New code needs focused tests in the owning package (`packages/*/tests/`), using `node:test` and
happy-dom. The four adapters render the same attribute contract; the shared scenarios in
`tests/fixtures/*-parity.json` are regenerated by the React tests with `UPDATE_PARITY=1`.

## Documentation

Docs live only in the READMEs (root and `packages/*`), in English, Vietnamese and Chinese with
the same structure. The `readme-system` skill under `.agents/skills/` describes the rules, and
`pnpm readme:check` enforces them.

## Compatibility policy (from 1.0)

- Public API: every export of an adapter entry, component props and events, the documented
  `data-*` attributes and ARIA roles, every `--chrono-*` property, the documented keyboard
  behavior and the value types.
- Breaking changes only in major versions. Deprecations are announced in a minor with a
  development warning and a README note, and removed in the next major at the earliest.
- Not public: core internals, `src/shared/`, the file layout inside `dist` and the exact text of
  development warnings.

## Releases (manual)

There is no CI and no release automation. Steps 1–5 can be prepared by anyone, including an
agent; steps 6–8 are the maintainer's.

1. `pnpm set-version <version>` (the same version in all nine packages (core, the four adapters and the four pickers); it refuses a lower one).
2. Update the changelog section of each package README (EN, VI, CN) by hand.
3. `pnpm release:check`.
4. `pnpm examples:build`; `pnpm examples:integrations` (report only).
5. `pnpm npm:publish:check` and inspect `artifacts/` (no `.css`, vendored core, no
   `@zealakit/chrono-core` dependency).
6. **Maintainer:** `pnpm npm:publish:all` (npm asks for the one-time password). Prereleases go to
   the `next` tag, releases to `latest`.
7. **Maintainer:** `git tag v<version>`, push the tag, write the GitHub release notes.
8. **Maintainer:** smoke-test a fresh install from npm and check `npm view <package> dist-tags`.

Agents never publish, tag, push or create releases.

## Reporting problems

Use the issue templates. A bug report needs a minimal reproduction link. For security issues
see `SECURITY.md`; for conduct concerns see `CODE_OF_CONDUCT.md`.
